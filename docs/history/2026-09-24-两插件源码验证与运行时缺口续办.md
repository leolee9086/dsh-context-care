## 关键源码结论

- `dsh-context-care/src/index.js` 在 `installContextCare` 中创建 `rewriteJournal`，并把同一个实例传入 `createRequestRewriter({ journal })`，最后 return `{ rewriteJournal }`。
- `dsh-context-care/src/host.js` 调用 `installContextCare` 并取 `care.rewriteJournal`，用同一实例注册 `/context-care/rewrite-journal`；journal 接线当前是正确的。
- `dsh-context-care/src/client.js` 轮询该路由并按 `sessionId:hash` 建表；`src/rewrite-view.js` 的 `createRewriteDefinition` 当前只接受 `content` 为数组，数组块只读取 `block.text`，并为 text/reasoning 同类多块补拼接 hash。Host `rewrite-journal.js` 已支持字符串 content、reasoning_content、thinking/text/reasoning/input_text/output_text 数组块、Responses reasoning.summary。
- 因而一个真实缺口是 Host 与 Client 内容形态判据不对称：客户端应至少支持 `content` 字符串、array 中 `thinking` 字段，并按 Responses message/summary 形式提取；否则 Host 已记 journal 但客户端 node 不产生对应 hash，卡片不出现。
- `dsh-context-care/src/index.js` 仍保留临时 probe 规则 id `probe-request-rewrite`，findRegex 源文本是 `/\\[\\[REWRITE-PROBE\\]\\]/g`，replaceString 是替换标记；这条规则需在真实验收完成后再决定删除，不能误删。
- `dsh-fetch-router/lib/rules.js` 中 `applyRewrite` 已将 `request: ctx.request` 传给 recorder，修复成功改写因记录回调访问 `entry.request.url` 而抛 `undefined.url` 的根因。
- `dsh-fetch-router/lib/rewrite.js` 已不吞改写异常，非法返回值抛 TypeError，原异常/cause/stack保留。`lib/interceptor.js` 用 `errorDetail` 记录完整错误链后重新抛出。

## 发现的验证脚本问题

`dsh-context-care/scripts/verify-fetch-rewrite.mjs` 的探针 body 第21行仍使用“替换后标记”，而规则匹配的是“触发标记”；不过脚本只断言服务端收到该字符串，不能证明规则真的命中。下步应在不输出可能被改写的标记的情况下修脚本：在脚本内由字符数组/拼接构造触发文本，断言发送结果不等于触发文本且等于替换文本，且输出只用长度/布尔值；不要凭肉眼重复标记。
